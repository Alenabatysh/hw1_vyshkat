## Описание проекта

Система управления парком устройств для сервисного центра. Программа позволяет учитывать транспорт (велосипеды, самокаты, электровелосипеды) и аксессуары (шлемы, зарядные и док-станции), проводить их техосмотр и получать статистику по парку.

### Доменная модель

Доменная модель построена на комбинации **интерфейсов** (для поведения) и **абстрактных классов** (для общей реализации).

#### Интерфейсы (поведение)

- **`IInventoryItem`** — базовый контракт для любого устройства парка. Содержит инвентарный номер и название.
- **`IEnergyConsumer`** — устройство, потребляющее энергию (кВт/ч). Реализуют только те устройства, у которых есть это свойство.
- **`IBeginnerFriendly`** — устройство с уровнем доступности для новичков.
- **`IInspectionService`** — контракт для сервиса техосмотра, который принимает решение о пригодности устройства.

**Почему интерфейсы, а не абстрактные классы?** В C# класс может наследовать только один абстрактный класс, но реализовывать несколько интерфейсов. Это позволяет комбинировать поведения: например, `ChargingStation` одновременно является `Accessory` и `IEnergyConsumer` — такое было бы невозможно при использовании абстрактных классов.

#### Абстрактные классы (общая реализация)

- **`Vehicle`** — базовый класс для транспорта. Реализует `IInventoryItem`, `IEnergyConsumer`, `IBeginnerFriendly`. От него наследуются `Bicycle`, `Scooter`, `ElectricBike`.
- **`Accessory`** — базовый класс для аксессуаров. Реализует только `IInventoryItem`. От него наследуются:
  - `Helmet` — не потребляет энергию
  - `ChargingStation` и `DockingStation` — дополнительно реализуют `IEnergyConsumer`

### Бизнес-логика

- **`ServiceCenter`** — реализует `IInspectionService`. Проверяет устройство: если оно потребляет энергию (`IEnergyConsumer`), расход не должен превышать 10 кВт·ч. Устройства без энергии (например, шлем) проходят проверку автоматически.

- **`FleetManager`** — менеджер парка устройств. Отвечает за:
  - Добавление устройств с проверкой через техосмотр
  - Проверку уникальности инвентарных номеров (бизнес-правило)
  - Предоставление статистики: суммарное потребление энергии, список устройств для новичков (уровень >= 6), список всех устройств парка

**Важно:** `FleetManager` не "отправляет" устройства в сервисный центр — он использует `IInspectionService` как инструмент для проверки при добавлении устройства в парк. Это реализация принципа Dependency Inversion: менеджер зависит от абстракции, а не от конкретной реализации техосмотра.

## Архитектура проекта

Проект разделён на 4 слоя с чётким разделением ответственности:

### Слои

#### 1. Domain (Доменная модель)
Содержит все интерфейсы (`IInventoryItem`, `IEnergyConsumer`, `IBeginnerFriendly`, `IInspectionService`) и классы сущностей (`Vehicle`, `Accessory`, `Bicycle`, `Scooter`, `ElectricBike`, `Helmet`, `ChargingStation`, `DockingStation`). Это самый нижний слой — он **ни от кого не зависит**.

#### 2. Application (Бизнес-логика)
Содержит:
- **`ServiceCenter`** — реализация техосмотра
- **`FleetManager`** — менеджер парка устройств
- **`SimpleContainer`** — DI-контейнер, который запоминает, как создавать объекты по переданным функциям, и возвращает новые экземпляры при необходимости

**Зависит от:** `Domain` (использует интерфейсы и классы сущностей)

#### 3. ConsoleApp (Пользовательский интерфейс)
Консольное приложение с интерактивным меню из 7 пунктов:
1. Добавить транспорт
2. Добавить аксессуар
3. Загрузить демо-данные
4. Показать все устройства парка
5. Показать суммарное потребление энергии
6. Показать список устройств для новичков (уровень >= 6)
7. Выход

При вводе некорректных данных приложение запрашивает повторный ввод до получения корректного значения.

**Зависит от:** `Application` и `Domain`

#### 4. Tests (Юнит-тесты)
Содержит 17 тестов:
- **`ServiceCenterTests`** — проверка техосмотра (валидные/невалидные устройства)
- **`FleetManagerTests`** — проверка менеджера парка (добавление, статистика, DI через Moq)
- **`ValidationTests`** — проверка валидации конструкторов (пустые строки, отрицательная энергия, уровень вне диапазона)

**Зависит от:** `Application` и `Domain`

**Важно:** `Domain` не зависит ни от кого — это фундамент системы. Все остальные слои зависят от него.

## Принципы SOLID

### S — Single Responsibility Principle (Принцип единственной ответственности)

**Формулировка:** У класса должна быть только одна причина для изменения.

**Применение в проекте:**
- **`ServiceCenter`** отвечает только за проверку устройств на пригодность. Если изменятся правила техосмотра — изменится только этот класс.
- **`FleetManager`** отвечает только за управление парком (добавление, статистика). Если изменится логика парка — изменится только этот класс.
- **`SimpleContainer`** отвечает только за DI. Если изменится логика контейнера — изменится только этот класс.

Каждый класс имеет одну зону ответственности, что делает код модульным и лёгким для поддержки.

---

### O — Open/Closed Principle (Принцип открытости/закрытости)

**Формулировка:** Классы должны быть открыты для расширения, но закрыты для модификации.

**Применение в проекте:**
- **Добавление нового транспорта:** Можно создать новый класс (например, `Monocycle`), наследующий от `Vehicle`. Не нужно менять `Vehicle`, `FleetManager` или `ServiceCenter` — они уже работают с интерфейсом `IInventoryItem`.
- **Добавление нового правила техосмотра:** Можно создать новый класс, реализующий `IInspectionService`. Не нужно менять `FleetManager` — он уже работает с интерфейсом.

Система расширяется без изменения существующего кода.

---

### L — Liskov Substitution Principle (Принцип подстановки Лисков)

**Формулировка:** Объекты подтипов должны быть заменяемы объектами базового типа без нарушения корректности программы.

**Применение в проекте:**
- `Bicycle`, `Scooter`, `ElectricBike` наследуют от `Vehicle` и могут использоваться везде, где ожидается `Vehicle`.
- `Helmet`, `ChargingStation`, `DockingStation` наследуют от `Accessory` и могут использоваться везде, где ожидается `Accessory`.

Например, метод `FleetManager.AddDevice(IInventoryItem device)` принимает любой объект, реализующий `IInventoryItem` — будь то `Bicycle`, `Scooter` или `Helmet`. Программа работает корректно с любым из них.

---

### I — Interface Segregation Principle (Принцип разделения интерфейсов)

**Формулировка:** Клиенты не должны зависеть от методов, которые не используют.

**Применение в проекте:**
- **`Helmet`** реализует только `IInventoryItem` — ему не нужны энергия и уровень доступности.
- **`ChargingStation` и `DockingStation`** реализуют `IInventoryItem` и `IEnergyConsumer` — им нужна энергия, но не нужен уровень.
- **`Vehicle`** реализует все три интерфейса (`IInventoryItem`, `IEnergyConsumer`, `IBeginnerFriendly`) — транспорту нужно всё.

Каждый класс реализует только те интерфейсы, которые ему действительно нужны. Это предотвращает нагромождение неиспользуемых методов.

---

### D — Dependency Inversion Principle (Принцип инверсии зависимостей)

**Формулировка:** Модули высокого уровня не должны зависеть от модулей нижнего уровня. Оба должны зависеть от абстракций.

**Применение в проекте:**
- **`FleetManager`** (модуль высокого уровня) зависит от `IInspectionService` (абстракция), а не от `ServiceCenter` (конкретная реализация).
- Это позволяет подменить техосмотр на любую другую реализацию (например, `AdvancedServiceCenter` или `MockServiceCenter` для тестов) без изменения `FleetManager`.

**Пример:**
```csharp
// FleetManager работает с интерфейсом
public FleetManager(IInspectionService inspectionService)
{
    _inspectionService = inspectionService;
}

// Можно передать любую реализацию
var manager = new FleetManager(new ServiceCenter());           // Реальная реализация
var testManager = new FleetManager(new MockServiceCenter());   // Мок для тестов
```

### Сознательные ограничения принципов

В проекте некоторые принципы SOLID реализованы не до максимума — это осознанное решение, основанное на принципе YAGNI (You Aren't Gonna Need It).

**Interface Segregation (I):** Интерфейсы `IInventoryItem`, `IEnergyConsumer`, `IBeginnerFriendly` могли бы быть разбиты на более мелкие (`IHasId`, `IHasName`, `IHasEnergyConsumption`). Однако для предметной области из 8 классов такое дробление привело бы к overengineering — избыточному количеству интерфейсов, которые усложнили бы понимание кода без реальной пользы. Текущий уровень дробления оптимален: каждый интерфейс несёт законченную смысловую нагрузку.

**Single Responsibility (S) в точке входа:** Файл `Program.cs` содержит несколько локальных функций (чтение ввода, обработка меню). Теоретически их можно было бы вынести в отдельные классы (`ConsoleMenu`, `UserInputReader`). Однако для небольшого консольного приложения это избыточно. SRP здесь применяется на уровне проекта: `Program.cs` — это точка входа, его единственная ответственность — "запустить приложение".

## Внедрение зависимостей (Dependency Injection)

В проекте реализован собственный легковесный DI-контейнер — класс `SimpleContainer`. Его основная задача — управление созданием объектов и обеспечение слабой связанности (loose coupling) между компонентами системы.

### Как это работает
- **`Register<TInterface>(Func<TInterface> factory)`**: сохраняет в контейнере сопоставление интерфейса с функцией-фабрикой, которая знает, как создать конкретный объект.
- **`Resolve<TInterface>()`**: извлекает эту функцию и возвращает новый экземпляр запрошенного типа.

### Пример использования в проекте
В точке входа (`Program.cs`) контейнер настраивает граф зависимостей перед запуском приложения:

```csharp
SimpleContainer container = new();
// 1. Запоминаем, как создавать ServiceCenter по запросу IInspectionService
container.Register<IInspectionService>(() => new ServiceCenter());

// 2. Запоминаем, как создавать FleetManager, внедряя в него зависимость из контейнера
container.Register<FleetManager>(() => new FleetManager(container.Resolve<IInspectionService>()));

// 3. Получаем полностью настроенный менеджер для работы
FleetManager manager = container.Resolve<FleetManager>();
```

## Расширяемость системы

### Сценарий 1: Добавление нового вида транспорта или аксессуара

**Что НЕ сломается:**
- Вся существующая бизнес-логика (`ServiceCenter`, `FleetManager`) продолжит работать без изменений.
- Все 18 юнит-тестов останутся зелёными.
- DI-контейнер продолжит корректно собирать зависимости.

**Что нужно сделать:**
1. Создать новый класс (например, `Monocycle`), наследующий от `Vehicle`.
2. Реализовать конструктор, вызывающий базовый конструктор `Vehicle`.
3. Добавить пункт меню в `Program.cs` для создания нового типа.

**Почему это работает:** `FleetManager` и `ServiceCenter` работают с интерфейсом `IInventoryItem`, а не с конкретными классами. Новый транспорт автоматически становится совместимым со всей существующей инфраструктурой. Это классическая демонстрация принципа **Open/Closed**: система открыта для расширения (новый класс), но закрыта для модификации (существующий код не меняется).

### Сценарий 2: Добавление новой характеристики (например, гарантия)

**Что НЕ сломается:**
- Существующие устройства продолжат работать, если не трогать их классы.

**Что нужно сделать (правильный путь без нарушения O/C):**
1. Создать новый интерфейс (например, `IHasWarranty` с методом `GetWarrantyPeriod()`).
2. Создать **новый класс** (например, `ElectricBikeWithWarranty`), который наследует от `ElectricBike` и реализует `IHasWarranty`.
3. **Важно:** существующий `ElectricBike` НЕ модифицируется — добавляется новый класс.
4. Если `ServiceCenter` должен учитывать гарантию при техосмотре, создать **новый** сервис `WarrantyAwareInspectionService`, реализующий `IInspectionService`.

**Почему это правильно:**
- Существующие классы (`ElectricBike`, `ServiceCenter`) не меняются — принцип O/C соблюдён
- Добавляются новые классы (`ElectricBikeWithWarranty`, `WarrantyAwareInspectionService`) — система открыта для расширения
- Все существующие тесты остаются зелёными

### Сценарий 3: Добавление новой сущности (сотрудник, склад запчастей)

**Что НЕ сломается:**
- Вся существующая система управления парком устройств продолжит работать.

**Что нужно сделать:**
1. Создать новые классы в слое `Domain` (например, `Employee`, `SparePart`).
2. Определить для них новые интерфейсы (`IEmployee`, `IWarehouseItem`).
3. Создать новые менеджеры в слое `Application` (например, `EmployeeManager`, `WarehouseManager`).
4. Зарегистрировать их в DI-контейнере.
5. Добавить пункты меню в `Program.cs`.

### Сценарий 4: Привязка устройств к клиентам (аренда)

**Что может сломаться:**
- Если добавить поле `Client` напрямую в базовые классы `Vehicle` и `Accessory` — это **нарушение O/C**, так как придётся модифицировать существующий код.
- Все существующие тесты могут потребовать обновления (конструкторы изменятся).
- Если добавить интерфейс `IRentable` к существующим классам (`Bicycle`, `Scooter`) — это тоже **нарушение O/C** (модификация существующих классов).

**Правильный путь (без нарушения O/C):**
1. Создать новый интерфейс `IRentable` с методом `AssignToClient(Client client)`.
2. Создать **новые классы**, которые наследуют от существующих и реализуют `IRentable`.

## Тестирование

Проект покрыт юнит-тестами на **90.8%** (требование >= 60%). Тесты разделены на 3 логических блока, каждый из которых отвечает за проверку определенного слоя системы:

### 1. ServiceCenterTests (2 теста)
Проверка логики техосмотра:
- `CheckItem_WithValidDevice_ReturnsTrue`: устройство с корректными данными и энергией <= 10 успешно проходит проверку.
- `CheckItem_WithEnergyAbove10_ReturnsFalse`: устройство с энергией > 10 отклоняется сервисом.

### 2. FleetManagerTests (7 тестов)
Проверка бизнес-логики управления парком:
- `AddDevice_WithValidDevice_ReturnsSuccess`: валидное устройство проходит техосмотр и добавляется в парк.
- `AddDevice_WithEnergyAbove10_ReturnsInspectionFailed`: устройство, не прошедшее техосмотр, не добавляется в парк.
- `AddDevice_WithSameId_ReturnsDuplicateNumber`: попытка добавить устройство с уже существующим инвентарным номером блокируется.
- `GetTotalEnergyConsumption_ReturnsExpectedResult`: корректный подсчет суммы энергии. *Примечание: проверка выполняется через `Math.Abs(expected - actual) < epsilon` для корректной работы с числами с плавающей точкой (`double`).*
- `GetBeginnerFriendlyDevices_ReturnsExpectedResult`: фильтрация устройств, возвращает только те, у которых уровень доступности >= 6.
- `GetAllDevicesInfo_ReturnsExpectedResult`: корректное формирование списка всех устройств с их ID и названиями.
- `DI_WorksProperly`: **ключевой тест**, демонстрирующий работу DI. В менеджер через конструктор передается `Mock<IInspectionService>`, который принудительно возвращает `true`. Тест подтверждает, что менеджер работает с абстракцией, а не с конкретной реализацией.

### 3. ValidationTests (9 тестов)
Проверка защитных механизмов (валидации) в конструкторах доменных классов. Тесты подтверждают, что при передаче невалидных данных выбрасывается `ArgumentException`:
- Пустой инвентарный номер или имя (для транспорта и аксессуаров).
- Отрицательное или нулевое значение потребления энергии (`<= 0`).
- Уровень доступности для новичков вне допустимого диапазона (1–10).

## Как запустить проект

### Требования
- Visual Studio 2022 (с установленной нагрузкой ".NET desktop development")
- .NET SDK 8.0 (устанавливается вместе с Visual Studio)

### Запуск консольного приложения
1. Склонируйте репозиторий или скачайте его архив.
2. Откройте файл `VyshKat.sln` в Visual Studio 2022 (двойной клик по файлу).
3. В **Обозревателе решений** (Solution Explorer) найдите проект `VyshKat.ConsoleApp`.
4. Нажмите на него правой кнопкой мыши ? **"Назначить запускаемым проектом"** (Set as Startup Project).
5. Нажмите `F5` (запуск с отладкой) или `Ctrl + F5` (запуск без отладки).
6. Откроется консоль с интерактивным меню — можно работать с программой.

### Запуск тестов
1. Откройте решение `VyshKat.sln` в Visual Studio.
2. В верхнем меню выберите **Тест ? Тестовый обозреватель** (Test ? Test Explorer) или нажмите `Ctrl + E, T`.
3. Нажмите кнопку **"Выполнить все"** (Run All) — все 18 тестов запустятся.
4. Зелёные галочки означают успешное прохождение.

### Альтернативный способ: через терминал
Для тех, кто предпочитает командную строку:

```bash
# Перейти в папку консольного приложения
cd VyshKat.ConsoleApp

# Восстановить зависимости (один раз)
dotnet restore

# Запустить приложение
dotnet run

# Запустить тесты
dotnet test

# Проверить покрытие кода
dotnet test --collect:"XPlat Code Coverage"
```
